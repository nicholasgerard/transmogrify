# Protocol contract

Source of truth for Transmogrify's wire-level and lifecycle claims about the
Codex app-server. Every claim carries one label:

| Label | Meaning |
| --- | --- |
| schema-derived | Present in JSON Schema generated by the named runtime |
| live-verified | Exercised against a named runtime on a dated receipt |
| implementation contract | Enforced by this repository and its tests |
| unverified | Deliberately not promised |

The minimum supported runtime is `0.151.0`. Dated receipts are collected in
[Compatibility tuple and verified receipts](#compatibility-tuple-and-verified-receipts).

Regenerate the schemas before changing a protocol claim:

```bash
SCHEMA_DIR="$(mktemp -d)"
codex app-server generate-json-schema --out "$SCHEMA_DIR"
```

Generated filenames below are relative to that output directory.

## Transport and handshake

**Boundary.** OpenAI documents stdio, WebSocket, and Unix-socket app-server
transports, and labels WebSocket experimental and unsupported for production.
Transmogrify's WebSocket path is a pinned loopback compatibility surface, not a
production transport support claim. See the
[official app-server reference](https://learn.chatgpt.com/docs/app-server).

**Implementation contract.** `scripts/lib/app-server.js`:

- accepts canonical `ws+unix:<normalized absolute socket path>` endpoints and
  literal `127.0.0.1` or `::1` URLs; loopback URLs refuse credentials,
  non-root paths, queries, and fragments, while Unix paths are bounded to 100
  UTF-8 bytes;
- accepts text frames only and caps each inbound WebSocket message at 8 MiB;
- bounds connection and request timeouts, separates client and server request
  IDs, validates response envelopes, and closes every unresolved call as
  transport-unknown;
- sends `initialize` with the experimental capability and, after a valid
  response, sends the `initialized` notification before returning control to
  callers;
- routes provider notifications to one generic notification channel, so
  reserved EventEmitter names cannot impersonate client lifecycle events;
- returns a fixed error when a custom server-request handler fails, without
  echoing local exception text.

Invalid JSON, non-object frames, non-string or control-bearing methods, array
parameters, and otherwise unrecognized envelopes are protocol violations: the
client closes the connection and projects every pending call as
transport-unknown.

`scripts/doctor.js` performs only this handshake and closes. A runtime outside
the supported `0.151.0`-or-newer range remains visible through the doctor's bounded
version report, but `rpc.js` and lifecycle mutations refuse it.

## Managed daemon and relay

**Implementation contract.** `scripts/runtime-up.sh` first checks the Codex
installer's managed standalone binary at
`<CODEX_HOME>/packages/standalone/current/codex`. It reads the running daemon
with `app-server daemon version`. Only when no daemon control socket exists may
it use `app-server daemon start`, followed by another version read and an
initialize-only probe of
`<CODEX_HOME>/app-server-control/app-server-control.sock`. It never calls
`daemon bootstrap`, `stop`, `restart`, or `enable-remote-control`.

Transmogrify connects to the daemon directly with `ws+unix:`. Codex Desktop,
which requires a loopback TCP WebSocket, reaches that same socket through
`scripts/lib/relay.js`. The relay binds only `127.0.0.1` or `::1`, forwards raw
bytes, caps and rotates its private log, and records its pid plus measured
process birth under the Transmogrify state root. Start reuses that exact live
record. An unrecorded listener is adopted only after the TCP and Unix endpoints
complete supported app-server handshakes with identical runtime identities.
Stop signals only the pid whose process birth still matches the record.

The default relay is `ws://127.0.0.1:8844/`; `TRANSMOGRIFY_RELAY_PORT` selects a
different deterministic port. Runtime selection is explicit `--url`, then
`TRANSMOGRIFY_URL`, then the live relay record, then the legacy standalone
`TRANSMOGRIFY_PORT`/8843 endpoint. If the daemon cannot be verified or started,
`runtime-up.sh` returns JSON that identifies the standalone fallback and its
reason.

**Live-verified, 2026-09-04.** Codex 0.151.0's managed daemon served the
app-server WebSocket protocol at both `/` and `/rpc` through its Unix control
socket. Two clients shared thread and turn notifications. Codex Desktop reached
the same daemon through a byte-forwarding loopback relay on port 8844. The
daemon's initialize user agent used its first client's product name, so
compatibility is judged by the version component.

**Schema-derived.** `JSONRPCMessage.json`, `JSONRPCRequest.json`, and
`JSONRPCResponse.json` define the JSON-RPC request, response, notification, and
error envelopes. `ClientRequest.json` includes `initialize`.
`v1/InitializeParams.json` carries `clientInfo` and `capabilities`; experimental
methods and fields are opted into with `capabilities.experimentalApi:true`.

**Live-verified.** The WebSocket runtime accepts one headerless JSON-RPC
document per text frame. The standalone client uses that framing; JSONL is not
used on its WebSocket path. Framing is a dated transport receipt, not a claim
derived from the generated message schemas.

## Native app visibility

A Codex lane renders and streams in Codex Desktop only while the app is a client
of the runtime that lane runs on. Attachment is measured, never inferred from a
successful handshake.

**Implementation contract.**

- `scripts/desktop-attach.js check` is read-only. It reports whether a Codex
  Desktop process (bundle `com.openai.codex`) holds an ESTABLISHED loopback
  connection to the selected runtime, with the client pid, the connection, the
  app version and build, and whether that build is on the tested list.
- `scripts/doctor.js` projects that receipt as `nativeVisibility.verified:true`
  with `nativeDispatchReady:true`. Otherwise it reports
  `desktop-attachment:<state>` with the next action.
- Codex spawn measures the receipt at dispatch time and records
  `visibility.state:"desktopAttached"` with the connection receipt. Without it,
  spawn refuses with `NATIVE_VISIBILITY_REQUIRED` and names the observed Desktop
  state, unless `--allow-protocol-only` labels a deliberately unattached lane.

**Mechanism, unverified as a vendor contract.** Codex Desktop becomes a client
of a standalone app-server when the app is launched with
`CODEX_APP_SERVER_WS_URL` set to that endpoint. Launched normally it starts its
own private bundled stdio child
(`Contents/Resources/codex -c features.code_mode_host=true app-server`) and
reports as unattached. The variable is read by the app's launcher and is not
published in OpenAI's app-server reference, so Transmogrify treats it as an
observed macOS mechanism with a measured receipt. A build that ignores the
variable never produces the receipt, and every consumer fails closed to the
protocol-only path.

A standalone listener on the selected endpoint (default `ws://127.0.0.1:8843`)
can return a `Codex Desktop/0.151.0` initialize user-agent while Desktop is
attached to nothing. The user-agent is not an attachment receipt.

**Implementation contract.** `scripts/desktop-attach.js ensure` reuses an
existing attachment, including one another operator established; launches
Desktop attached when it is not running; and quits and relaunches a running
unattached Desktop only with `--relaunch-desktop` or the standing
`TRANSMOGRIFY_DESKTOP_RELAUNCH=auto`. It refuses with `DESKTOP_HOST_SESSION`
when the command itself runs inside a Desktop-hosted session, because the
relaunch would end that session, and it reports `ATTACHED_ELSEWHERE`,
`RUNTIME_UNAVAILABLE`, `ATTACH_TIMEOUT`, and `DESKTOP_QUIT_TIMEOUT` rather than
forcing an outcome. It quits Desktop only through the app's own application
quit, never kills a process, and never starts, stops, or reconfigures the
runtime.

A runtime this installation launches carries
`-c mcp_servers.codex_app={command="",enabled=false}`, which keeps the
Desktop-only `codex_app` MCP bridge off; Desktop thread-opens were observed
failing on an attached runtime launched without that override. A reused listener
keeps its own configuration.

**Boundary.** Codex Desktop's private bundled child has no documented external
attachment path. Bundled `app-server proxy` rejected Desktop's private
`ipc.sock`, and the bundled app tools MCP accepted an external MCP initialize
but closed its host pipe on tool listing. These read-only receipts establish the
current boundary; they do not authorize using either private socket as a control
plane.

### Seat ownership

**Implementation contract.** Spawn reserves a durable lane and seat before
sending `thread/start`. `v2/ThreadStartParams.json` permits an explicit `cwd`;
`v2/ThreadStartResponse.json` requires both a top-level `cwd` and a thread whose
required `cwd` is the working directory captured for that thread. The adapter
requires both returned paths to equal the exact reserved seat before it sends
the first input. A missing or non-string value is a protocol-shape failure; a
different well-formed path is an ownership mismatch. Either post-creation
failure preserves the returned provider ID as partial success, marks the lane
delivery-unknown, and dispatches no turn. The immutable creation receipt records
the requested path and each provider-observed path separately, using `null` when
required provider metadata is absent.

**Schema-derived and implementation contract.** `v2/ThreadReadResponse.json`
requires the returned thread's `cwd`. Every status read and every later Codex
mutation requires it to match the lane's durable seat before provider state is
accepted or another mutation is sent. `v2/ThreadResumeParams.json` and
`v2/TurnStartParams.json` permit an explicit `cwd`; the adapter supplies the
owned seat to both. `v2/ThreadResumeResponse.json` requires both a top-level
`cwd` and a thread `cwd`; both must match before the boundary input is sent.

### Input receipt

**Implementation contract.** The adapter starts the first turn with the same
explicit seat and a durable operation UUID in `clientUserMessageId`, and
requires the correlated `turn/start` response for the exact returned turn ID.
Generated `v2/TurnStartResponse.json` permits the response item to carry the
operation UUID as `userMessage.clientId`. When that exact marker and the
journaled input hash are present, the response is the input receipt. When the
response omits the marker, the adapter instead pages `thread/items/list` and
accepts only the same turn ID plus the exact marker/content receipt. Duplicate
exact response markers, an exact response marker with different content, or a
persisted receipt for another turn fails closed.

Recovery uses the same persisted receipt and never treats a notification as
delivery acknowledgment or replays the input. The adapter then sets the exact
thread name and reads it back before returning success. A failure after
`thread/start` is partial or unknown; the adapter observes and repairs the exact
recorded operation and does not replay the initial input.

**Live-verified.** A disposable `turn/start` response omitted the exact client
marker even though the persisted `thread/items/list` row carried the matching
`clientId`, input, and turn ID, and the same method transiently returned the
exact message `thread/items/list is not supported yet` before the turn
materialized. The adapter retries only that measured precondition response,
within fixed attempt, delay, and aggregate pagination/row bounds; transport
failures and every other RPC error remain unknown or fail closed. This is why
the persisted receipt is part of the normal spawn and boundary-resume contract
rather than only a transport-loss recovery path.

### Name and provenance

**Implementation contract.** Before reservation or provider creation, the
adapter canonicalizes the requested summary to one native ownership marker:
`::: <summary>`. The marker is visual only; durable backend and provider
identifiers remain the ownership authority.

Every managed spawn is reserved under an exact installation-owned parent context
before provider mutation. The first child message begins with the bounded
Transmogrify provenance block defined in [Dispatch and lineage](DISPATCH.md),
followed by the caller's input. The block contains safe display labels and
durable Transmogrify references; it never contains repository paths, provider
credentials, or provider-private IDs. Provider acknowledgement applies to the
entire prefixed input, and the durable operation receipt hashes that exact
content.

### Execution profile

**Schema-derived.** `v2/ThreadStartParams.json` and `v2/ThreadResumeParams.json`
permit persistent `model` and `serviceTier` fields. `v2/TurnStartParams.json`
permits `model`, `effort`, persistent `serviceTier`, and turn-only
`serviceTierForTurn`; its generated description identifies the turn-only
`"default"` value as Standard execution.

**Implementation contract.** The adapter compiles Standard to the explicit
provider value `"default"` and Fast to `"priority"`. It supplies the persistent
field conservatively as well as the schema-described turn-only field, rather
than claiming omission means Standard or claiming the generated schema defines
the persistent field's semantics. It reapplies the resolved model, effort, and
tier on creation and every later execution boundary, including recovery, and
refuses a contradictory provider receipt. The selection contract and live model
catalog are documented in [Execution profiles](EXECUTION-PROFILES.md).

### Sandbox and approvals

**Implementation contract.** Transmogrify's Codex adapter starts every thread
with `sandbox:"workspace-write"` and `approvalPolicy:"never"`; `lane.js` exposes
no override. An action that requires unavailable approval must fail or return to
the host rather than silently broadening lane authority.

### Unreceipted spawns

**Known protocol boundary.** Generated `ThreadStartParams` exposes no client
idempotency token. A process can fail after the server creates a thread but
before the returned thread ID becomes durable. The adapter records this as
unknown, raises one parent attention event for the lane, and refuses blind
replay. A server-supported idempotency key would close this window.

**Implementation contract.** When the thread ID is durable but the first
`turn/start` has no receipt, the spawn journal stays open and reconciliation
never replays the input. Only an exact retirement closes it: the adapter
re-inspects the thread, refuses while the newest turn is `inProgress`, pages
`thread/items/list` for the exact client-message receipt one more time, and then
either completes the journal with the recovered turn or marks it failed as
superseded by retirement before archiving the thread.

## Steering and turn selection

**Implementation contract.** The adapter pages `thread/turns/list`, validates
the response shape, orders turns, and selects only the newest turn. If the
newest turn is not `inProgress`, steer and interrupt refuse. This rule handles a
measured runtime condition in which crash-orphaned older turns remain
`inProgress` indefinitely.

**Schema-derived.** `v2/TurnSteerParams.json` requires `threadId`,
`expectedTurnId`, and `input`. The expected turn ID is a precondition, not a
hint. `v2/TurnInterruptParams.json` requires both `threadId` and `turnId`.

**Live-verified.** A mid-turn steer was acknowledged on the same turn ID and
rendered as a user message in the native Codex app. Steering a thread whose
newest turn was not active returned the operation-specific JSON-RPC precondition
error, which `lane.js steer` reports as `NO_ACTIVE_TURN` with exit 2.

**Schema-derived, not yet live-verified.** `v2/TurnSteerParams.json` accepts
an optional `clientUserMessageId` with the same shape as
`TurnStartParams.clientUserMessageId`, and `v2/TurnSteerResponse.json` carries
only `turnId`. The adapter sends the steer operation id as that marker and
reconciliation looks for it among the target turn's `userMessage` items, so a
steer whose outcome was lost can be settled from the persisted receipt. The
first live steer recovery should be recorded here.

`thread/read {includeTurns:true}` returned `list_turns is not supported yet`
even though `includeTurns` appears in `v2/ThreadReadParams.json`. Use
`thread/turns/list`; never infer turn history from `thread/read` on this runtime
line.

**Unverified and unsupported.** Generated `v2/TurnSteerParams.json` defines an
`AdditionalContextEntry`, but its request `properties` do not expose an
`additionalContext` member. Do not send that orphaned definition. Treat
tool-observed text as untrusted at the host policy boundary instead.

## Status and listening

**Implementation contract.** The listener opens with paged `thread/list`
requests using an explicit all-source `sourceKinds` set and
`useStateDbOnly:true`, both defined by `v2/ThreadListParams.json`. In `--all`
mode it watches only owned threads active in that opening snapshot. It requires
the exact owned row's schema-required `cwd` to match the durable lane seat
before accepting its status. For each active owned lane it establishes a
metadata-only `thread/resume {cwd:<seat>,excludeTurns:true}` subscription,
requires both returned cwd fields to match, and retains seat-verified
`thread/read` polling as a fallback.

Do not rely on cross-client notification broadcast. The supported behavior is
subscription-scoped and every event handler filters exact watched IDs.

**Schema-derived.** `v2/ThreadStatusChangedNotification.json` defines status
types `active`, `idle`, `systemError`, and `notLoaded`, plus the active flags
`waitingOnApproval` and `waitingOnUserInput`.

`notLoaded` is normal persisted state. It is actionable only when a lane that
was expected to be working transitions there. A non-empty active flag wakes the
operator as `WAITING`; `idle`, `systemError`, and unexpected `notLoaded` wake it
as stopped/error boundaries.

**Live-verified.** A read-only census returned a large majority of persisted
rows as `notLoaded`, confirming that it is not itself proof of a dead runtime.
Process listings, silence, and client exit are likewise not lane liveness
receipts.

## Listing, reads, and diagnostics

**Implementation contract.** `scripts/rpc.js` is default-deny and permits only:

- `account/rateLimits/read`
- `model/list`
- `thread/items/list`
- `thread/list`
- `thread/loaded/list`
- `thread/read`
- `thread/turns/list`

Content-bearing thread reads require `--repo-root`, an exact registry-owned
Codex thread ID, and a matching recorded runtime identity. Notifications are
redacted. Thread census results retain only status, timestamps, and source;
thread IDs, parent IDs, previews, names, local paths, and Git metadata are
removed from unrelated rows. There is no mutation override.

Pagination cursors are opaque transport values and are never printed by the
routine census projection. Direct `model/list` and `account/rateLimits/read`
calls intentionally return provider metadata; treat that output as sensitive and
do not place it in public logs.

**Schema-derived.** `v2/ThreadListParams.json` and `v2/ThreadListResponse.json`
define cursor pagination. Follow `nextCursor` until null before claiming a
complete census.

## Retirement

**Implementation contract.** Retirement requires a durable harvest SHA-256
before any provider mutation. The adapter proves the newest turn is inactive,
sends archive once, scans the complete bounded archived listing, and requires
exactly one matching thread whose schema-required `cwd` equals the durable lane
seat. Missing, malformed, mismatched, or duplicate exact rows fail closed before
provider retirement is marked verified. A managed worktree is removed only when
it was clean at harvest, its current HEAD matches the harvest receipt, and its
current tracked, untracked, and ignored-file census is clean. An external seat
is never removed. Once a harvest or cleanup check observes dirt or changed HEAD,
automatic cleanup is permanently blocked pending manual review; later
cleanliness does not make the seat eligible again.

The census protects every file observed before removal, but Git worktree removal
is not atomic with it: another process running as the same user can write a new
ignored file after the final check and before Git removes the seat. Stop the
owned lane/provider execution before cleanup, and do not let unrelated local
writers target a managed seat during retirement. That same-user concurrency
window is outside Transmogrify's isolation boundary.

If cleanup fails after archive verification, the lane remains provider-retired
with a pending cleanup journal. A transient local Git/filesystem failure is
`CLEANUP_RETRYABLE`; a later retry performs no provider mutation. An observed
dirt, changed HEAD, seat/repository mismatch, or other unsafe invariant is
`CLEANUP_BLOCKED` and remains preserved for manual review. Preserving the seat
leaves the refusal intact. After the owner manually removes the exact managed
seat, only an exact-lane retirement with `--accept-manual-seat-removal` can
journal that acknowledgement; it rejects a surviving path entry or Git worktree
row and requires the preserved branch at the harvested HEAD. Fleet-wide
reconciliation cannot infer acknowledgement from disappearance. If the process
stops after an ordinary eligible Git removal but before the operation journal
closes, the next retry verifies the absence and completes the journal without
this manual-removal gate.

**Schema-derived.** `v2/ThreadArchiveParams.json` identifies the thread to
archive and `v2/ThreadArchiveResponse.json` defines the acknowledgment.

## Durable state and failure classes

**Implementation contract.** The ownership registry lives under
`TRANSMOGRIFY_STATE_DIR` or the platform state directory, outside the repository
and Git common directory. It records an installation UUID, canonical repository
identity, lane IDs, exact provider identities, seat identities, capability
semantics, and one pending operation pointer per lane. Operation details are
monotonic: phase transitions atomically replace the record, existing detail keys
are immutable, and later phases may add new receipt keys. The record is durable,
but it is not an append-only transition log.

Every operation record names one of seven types (`spawn`, `steer`, `stop`,
`recover`, `resume`, `interrupt`, `retire`) and holds only a state
enumerated for that type; a write outside the table is refused before it
reaches disk. Records carry `schemaVersion` (absent means 1). The registry
and the records are migrated on read when an upgrade path exists; a state
directory written by a newer Transmogrify is refused with an upgrade
instruction rather than reinterpreted. `abandon` is the only owner-authorized
way to close a journal without a provider receipt: it ends a non-retirement
operation as failed with the owner's reason and an unknown provider outcome.

State directories are current-user-owned mode `0700`, and JSON records are mode
`0600`. Managed `WORKTREES` roots are current-user-owned mode `0700`; configured
roots refuse a group/world-writable nearest existing ancestor.

Mutations use three outcomes:

| Outcome | Meaning | Required next action |
| --- | --- | --- |
| Confirmed | Exact provider receipt observed | Continue lifecycle |
| Not delivered | Provider mutation proven absent | A new authorized operation may be attempted |
| Unknown | Provider may have received it | Observe and reconcile; never replay blindly |

Public error projection defaults to `Unknown`. Only an explicit, tested
non-delivery or pre-dispatch refusal may report `Not delivered` or
`notAttempted`. A multi-stage failure may report a verified earlier phase, for
example Claude stop verified with archive not attempted, without claiming the
whole retirement succeeded.

Every command shares one exit table: 0 for a confirmed result, 2 for a usage
error or a safe refusal that attempted nothing, 3 for a failure or an
uncertain outcome after an attempt, and 1 only for an unexpected internal
error. A `doctor.js` result that is not ready and a `desktop-attach.js check`
that finds no attachment are reported as results and exit 3 without any
provider mutation. Failure envelopes use the fixed public text per code in
`scripts/lib/public-error.js`; a test asserts that every code a command can
throw has an entry. Server JSON-RPC errors preserve numeric `code` and string
`message` internally as defined by `JSONRPCErrorError.json`; routine public
CLI output never echoes them.

Claude runtime and worker epochs are append-only identity receipts inside the
current lane record. Reconciliation may add a verified CLI transition only when
the account, config, provider IDs, seat, worker binary, process birth, and
socket identity remain exact; it never overwrites the spawn runtime. See
[Claude Code integration](CLAUDE-CODE.md#measured-compatibility-tuple).

Parent/child delivery is also durable state, not a transient process callback.
An exact parent context owns immutable dispatch reservations and sequenced child
events. The parent must acknowledge an event by its exact ID and digest; a
missing or malformed acknowledgement cannot suppress redelivery. Every
unacknowledged event is returned again after a parent restart regardless of a
newer observation cursor. Observation may reconcile an exact incomplete spawn
journal, but it never infers provider creation from a title or elapsed time and
never replays an unknown mutation. The complete parent loop and event meanings
are in [Dispatch and lineage](DISPATCH.md).

## Security-relevant schema surface

**Schema-derived.** `ClientRequest.json` exposes authority-bearing methods
beyond the adapter. `v2/ThreadShellCommandParams.json` describes unsandboxed
full-access command execution. `v2/FsRemoveParams.json` accepts an absolute path
and recursive removal. `v2/ThreadDeleteParams.json` deletes by thread ID.

Transmogrify's accepted root-path loopback configuration is therefore an
unauthenticated local control plane, not a safe general-purpose localhost API.
Codex documents authenticated remote WebSockets, but Transmogrify rejects
non-loopback endpoints and URL credentials. Bind the selected local runtime to
`127.0.0.1`, inspect listeners and clients, and never expose a generic mutation
proxy.

## Mobile and remote hosts

**Boundary.** OpenAI's
[Remote connections documentation](https://learn.chatgpt.com/docs/remote-connections)
defines ChatGPT Desktop as the host paired with a phone. The phone sends prompts
and follow-ups while that connected host supplies the execution environment;
setup begins in Desktop and is not available through the Codex CLI or IDE
extension. Closing Desktop, host sleep, or network loss suspends Remote access
until the host returns. The generated app-server schema does not define that
device pairing or promise that an independently managed WebSocket runtime will
be adopted again after a Desktop restart. Transmogrify therefore treats native
mobile execution as a separate live host-integration receipt, never as a
consequence of a successful app-server handshake.

**Live-verified open seam.** Visibility is not a sufficient execution receipt.
After a Codex Desktop restart, an exact owned pre-restart lane stayed visible on
mobile, but mobile-originated input returned a server error and never appeared
in the shared runtime's exact thread items; a lane created after the same
restart accepted mobile input, persisted it exactly once, and replied. The
shared WebSocket runtime and the restarted Desktop app were serving distinct
app-server processes, and a native Desktop turn rehydrated the affected lane's
display but not its mobile input path. The open compatibility seam is
pre-restart lane reattachment, not post-restart creation or general mobile
execution, and the receipt does not identify the upstream failing RPC. Repairs
are in [Troubleshooting](TROUBLESHOOTING.md#codex-mobile-remote-access).

**Boundary and unverified.** OpenAI documents Desktop-managed SSH projects in
which Desktop starts and manages a Codex app-server on the remote host. Codex
CLI `0.151.0` help exposes `app-server daemon bootstrap` for durable SSH-driven
app-server management and `app-server proxy --sock` for proxying stdio to its
control socket; neither command appears in the official app-server reference.
Neither the official documentation nor that local help receipt establishes that
Desktop uses the daemon/proxy path or that a second exact client may safely
share it. Both remain unverified until a disposable live acceptance run proves
process ownership, multi-client notification delivery, and the full native
lifecycle.

## Runtime compatibility evidence

Lifecycle mutations require both a supported runtime version and a `good`
compatibility receipt for the connected version. The client measures missing
or expired evidence before sending a mutation. A failed measurement refuses
with `RUNTIME_UNSUPPORTED` and names `failingMethod`.

`thread/list` requires a validated successful response. The sentinel probes
for `turn/steer`, `thread/name/set`, and `thread/archive` require an exact,
method-specific not-found error containing the nil thread ID. Only error code
`-32600` with the complete measured message qualifies. Unknown methods,
missing fields, internal errors, and an unexpected success all fail.

The error patterns were measured on `0.151.0` and `0.153.4`. Other supported
versions use the newest measured patterns and explicitly identify that fallback
in the receipt. `thread/turns/list` starts `unmeasured`; it is never probed
against the nil thread. A validated read after the adapter verifies an exact
owned thread and its seat records positive turns-list evidence.

Compatibility receipts use `version: 2`. The cache key includes both runtime
version and probe-set version. Definitive failed measurements expire after
24 hours. Transport failures and exhausted deadlines never become persistent
incompatibility. Unmeasured turns-list capability does not fail the required
probe set. No raw runtime error text is stored in the receipt.

## Claude Code protocol boundary

Claude Code exposes a documented multi-session Remote Control server, but no
documented external local RPC equivalent to the Codex app-server lifecycle was
found in the surfaces verified for this release. Its public CLI follow-up,
measured local execution identity, Remote Control visibility, and pinned private
archival behavior are documented separately in
[CLAUDE-CODE.md](CLAUDE-CODE.md). Those claims are not derived from the Codex
schema.
