# Protocol contract

This document is the source of truth for wire-level and lifecycle claims in
Transmogrify. Claims are labeled:

- **schema-derived**: present in JSON Schema generated by the named runtime;
- **live-verified**: exercised against a named runtime on the stated date;
- **implementation contract**: enforced by this repository and its tests;
- **unverified**: deliberately not promised.

Generate the Codex schemas before changing a protocol claim:

```bash
SCHEMA_DIR="$(mktemp -d)"
codex app-server generate-json-schema --out "$SCHEMA_DIR"
```

The receipts below were refreshed against Codex app-server `0.151.0` on
2026-09-02. The supported runtime line is `0.151.x`; generated filenames are
relative to that output directory.

## Transport and handshake

**Official product boundary, checked 2026-09-02:** OpenAI documents stdio,
WebSocket, and Unix-socket app-server transports, but labels WebSocket
experimental and unsupported for production. Transmogrify's WebSocket path is
therefore a pinned loopback compatibility surface, not a production transport
support claim. See the
[official app-server reference](https://learn.chatgpt.com/docs/app-server).

**Schema-derived:** `JSONRPCMessage.json`, `JSONRPCRequest.json`, and
`JSONRPCResponse.json` define the JSON-RPC request, response, notification, and
error envelopes.

**Live-verified 2026-09-01 and implementation contract:** the WebSocket runtime
accepts one headerless JSON-RPC document per text frame. The standalone client
uses that framing; JSONL is not used on its WebSocket path. Framing is a dated
transport receipt, not a claim derived from the generated message schemas.

**Schema-derived:** `ClientRequest.json` includes `initialize`.
`v1/InitializeParams.json` carries `clientInfo` and `capabilities`; experimental
methods and fields are opted into with `capabilities.experimentalApi:true`.

**Implementation contract:** `scripts/lib/app-server.js` accepts only literal
`127.0.0.1` or `::1` URLs and refuses URL credentials, non-root paths, queries,
and fragments. It accepts text frames only and caps each inbound WebSocket
message at 8 MiB. It bounds connection and request timeouts, separates client and server request IDs,
validates response envelopes, and closes all unresolved calls as
transport-unknown. It sends `initialize` with the experimental capability and,
after a valid response, immediately sends the `initialized` notification before
returning control to callers. `scripts/doctor.js` performs only this handshake
and closes. Provider notifications always reach one generic notification
channel; reserved EventEmitter names cannot impersonate client lifecycle
events. A custom server-request handler failure returns a fixed error without
echoing local exception text. Invalid JSON, non-object frames, non-string or
control-bearing methods, array parameters, and otherwise unrecognized envelopes
are protocol violations: the client closes the connection and projects every
pending call as transport-unknown.

**Live-verified 2026-09-01:** the shared loopback runtime completed this
handshake and returned a `0.151.0` user-agent. A version outside the supported
`0.151.x` line remains visible through the doctor's bounded version report, but
`rpc.js` and lifecycle mutations refuse it.

## Codex lane lifecycle

| Lifecycle step | Request/notification | Generated schema receipt |
| --- | --- | --- |
| Create thread | `thread/start` | `v2/ThreadStartParams.json`, `v2/ThreadStartResponse.json` |
| Name thread | `thread/name/set` | `v2/ThreadSetNameParams.json` |
| Start turn | `turn/start` | `v2/TurnStartParams.json`, `v2/TurnStartResponse.json` |
| Find exact input receipt | `thread/items/list` | `v2/ThreadItemsListParams.json`, `v2/ThreadItemsListResponse.json` |
| Steer active turn | `turn/steer` | `v2/TurnSteerParams.json`, `v2/TurnSteerResponse.json` |
| Interrupt turn | `turn/interrupt` | `v2/TurnInterruptParams.json` |
| Read metadata | `thread/read` | `v2/ThreadReadParams.json`, `v2/ThreadReadResponse.json` |
| List turns | `thread/turns/list` | `v2/ThreadTurnsListParams.json`, `v2/ThreadTurnsListResponse.json` |
| Resume thread | `thread/resume` | `v2/ThreadResumeParams.json`, `v2/ThreadResumeResponse.json` |
| Observe state | `thread/status/changed` | `v2/ThreadStatusChangedNotification.json` |
| List threads | `thread/list` | `v2/ThreadListParams.json`, `v2/ThreadListResponse.json` |
| Archive thread | `thread/archive` | `v2/ThreadArchiveParams.json`, `v2/ThreadArchiveResponse.json` |

**Implementation contract:** spawn reserves a durable lane and seat before
sending `thread/start`. `v2/ThreadStartParams.json` permits an explicit `cwd`;
`v2/ThreadStartResponse.json` requires both a top-level `cwd` and a thread whose
required `cwd` is the working directory captured for that thread. The adapter
requires both returned paths to equal the exact reserved seat before it sends
the first input. A missing or non-string value is a protocol-shape failure; a
different well-formed path is an ownership mismatch. Either post-creation
failure preserves the returned provider ID as partial success, marks the lane
delivery-unknown, and dispatches no turn. The immutable creation receipt records
the requested path and each provider-observed path separately, using `null` when
required provider metadata is absent.

The adapter starts the first turn with the same explicit seat and a durable
operation UUID in `clientUserMessageId`, and requires the correlated
`turn/start` response for the exact returned turn ID. Generated
`v2/TurnStartResponse.json` permits the response item to carry the operation UUID
as `userMessage.clientId`. When that exact marker and the journaled input hash
are present, the response is the input receipt. When the response omits the
marker, the adapter instead pages `thread/items/list` and accepts only the same
turn ID plus the exact marker/content receipt. Duplicate exact response markers,
an exact response marker with different content, or a persisted receipt for
another turn fails closed. Recovery uses the same persisted receipt and never
treats a notification as delivery acknowledgment or replays the input. The
adapter then sets the exact thread name and reads it back before returning
success. A failure after `thread/start` is partial or unknown; the adapter
observes and repairs the exact recorded operation and does not replay the
initial input.

Before reservation or provider creation, the adapter canonicalizes the requested
summary to one native ownership marker: `::: <summary>`. The marker is visual
only; durable backend and provider identifiers remain the ownership authority.

**Implementation contract:** every managed spawn is reserved under an exact
installation-owned parent context before provider mutation. The first child
message begins with the bounded Transmogrify provenance block defined in
[Dispatch and lineage](DISPATCH.md), followed by the caller's input. The block
contains safe display labels and durable Transmogrify references; it never
contains repository paths, provider credentials, or provider-private IDs.
Provider acknowledgement applies to the entire prefixed input, and the durable
operation receipt hashes that exact content.

**Schema-derived and implementation contract:** `v2/ThreadReadResponse.json`
requires the returned thread's `cwd`. Every status read and every later Codex
mutation requires it to match the lane's durable seat before provider state is
accepted or another mutation is sent. `v2/ThreadResumeParams.json` and
`v2/TurnStartParams.json` permit an explicit `cwd`; the adapter supplies the
owned seat to both. `v2/ThreadResumeResponse.json` requires both a top-level
`cwd` and a thread `cwd`; both must match before the boundary input is sent.

**Schema-derived:** `v2/ThreadStartParams.json` and
`v2/ThreadResumeParams.json` permit persistent `model` and `serviceTier` fields.
`v2/TurnStartParams.json` permits `model`, `effort`, persistent `serviceTier`,
and turn-only `serviceTierForTurn`; its generated description identifies the
turn-only `"default"` value as Standard execution.

**Implementation contract:** the adapter compiles Standard to the explicit
provider value `"default"` and Fast to `"priority"`. It supplies the persistent
field conservatively as well as the schema-described turn-only field, rather
than claiming omission means Standard or claiming the generated schema defines
the persistent field's semantics. It reapplies the resolved model, effort, and
tier on creation and every later execution boundary, including recovery, and
refuses a contradictory provider receipt. The selection contract and live
model catalog are documented in [Execution profiles](EXECUTION-PROFILES.md).

**Live-verified against app-server 0.151.0 on 2026-09-01:** a disposable
`turn/start` response omitted the exact client marker even though the persisted
`thread/items/list` row carried the matching `clientId`, input, and turn ID. The
same method transiently returned the exact message `thread/items/list is not
supported yet` before the turn materialized. The
adapter retries only that measured precondition response within fixed attempt,
delay, and aggregate pagination/row bounds;
transport failures and every other RPC error remain unknown or fail closed. It
recovered the exact receipt, repaired the intended disposable name, and archived
the task with verified managed-seat cleanup. This runtime behavior is why the
persisted receipt is part of the normal spawn and boundary-resume contract
rather than only a transport-loss recovery path.

**Live-verified 2026-09-02:** Codex lanes created from both Codex and Claude
hosts rendered in Codex Desktop `26.825.51511` (`7377`) and ChatGPT for iOS
`1.2026.230` (`32543289983`). These are exact client-build receipts, not a claim
about unmeasured or future client builds.

**Official product boundary, checked 2026-09-02:** OpenAI's
[Remote connections documentation](https://learn.chatgpt.com/docs/remote-connections)
defines ChatGPT Desktop as the host paired with a phone. The phone sends prompts
and follow-ups while that connected host supplies the execution environment;
setup begins in Desktop and is not available through the Codex CLI or IDE
extension. Closing Desktop, host sleep, or network loss suspends Remote access
until the host returns. The generated app-server schema does not define that
device pairing or promise that an independently managed WebSocket runtime will
be adopted again after a Desktop restart. Transmogrify therefore treats native
mobile execution as a separate live host-integration receipt, never as a
consequence of a successful app-server handshake.

**Live-verified boundary on app-server 0.151.0, 2026-09-02:** after a Codex
Desktop restart, mobile rediscovered an exact owned lane and its managed
worktree but mobile-originated input returned a server error. A native Desktop
turn successfully rehydrated the same lane and restored its correct project
display; a second fresh mobile input still failed and never appeared in the
shared runtime's exact thread items. The shared WebSocket runtime and the
restarted Desktop app were serving distinct app-server processes. This receipt
does not identify the upstream failing RPC, but it does establish that
visibility is not a sufficient execution receipt. A separately owned lane
created after the same restart accepted a mobile-originated input, persisted it
exactly once, and returned a visible reply. The open compatibility seam is
therefore pre-restart lane reattachment, not post-restart creation or general
mobile execution.

**Live-verified runtime topology, 2026-09-02:** ChatGPT Desktop
`26.831.21537` (`7579`) launched bundled Codex `0.152.1` as its own private
stdio child while a standalone `0.151.0` app-server continued listening on
`ws://127.0.0.1:8843`. Desktop held no connection to that WebSocket runtime.
The `Codex Desktop/0.151.0` initialize user-agent returned by the standalone
listener therefore did not prove Desktop process attachment. Bundled
`app-server proxy` rejected Desktop's private `ipc.sock`, and the bundled app
tools MCP accepted an external MCP initialize but closed its host pipe on tool
listing. OpenAI's documented app-server transports do not define an external
attachment path to Desktop's private child. These read-only receipts establish
the current boundary; they do not authorize using either private socket as a
control plane.

**Official SSH-host boundary, checked 2026-09-02:** ChatGPT Desktop's local
bundled private stdio child has no documented external attachment path.
Separately, OpenAI documents Desktop-managed SSH projects in which Desktop
starts and manages a Codex app-server on the remote host.

**Local CLI-help receipt, checked 2026-09-02:** Codex CLI `0.151.0` exposes
`app-server daemon bootstrap` for durable SSH-driven app-server management and
`app-server proxy --sock` for proxying stdio to its control socket. These
commands are not documented in the official app-server reference. Neither the
official documentation nor this local help receipt establishes that Desktop
uses that daemon/proxy path or that a second exact client may safely share it.
Both remain unverified until a disposable live acceptance run proves process
ownership, multi-client notification delivery, and the full native lifecycle.

**Implementation contract:** the standalone Codex CLI fixes new turns to
`sandbox:"workspace-write"` and `approvalPolicy:"never"`. The public CLI does
not expose overrides in this release; an action that requires unavailable
approval must fail or return to the host rather than silently broadening lane
authority.

**Known protocol boundary:** generated `ThreadStartParams` exposes no client
idempotency token. A process can fail after the server creates a thread but
before the returned thread ID becomes durable. The adapter records this as
unknown and refuses blind replay. A server-supported idempotency key would close
this window.

## Steering and turn selection

**Schema-derived:** `v2/TurnSteerParams.json` requires `threadId`,
`expectedTurnId`, and `input`. The expected turn ID is a precondition, not a
hint. `v2/TurnInterruptParams.json` requires both `threadId` and `turnId`.

**Live-verified 2026-09-01:** a mid-turn steer was acknowledged on the same turn
ID and rendered as a user message in the native Codex app. Steering a thread
whose newest turn was not active returned the operation-specific JSON-RPC
precondition error and `scripts/steer.js` exited 2.

**Implementation contract:** the adapter pages `thread/turns/list`, validates
the response shape, orders turns, and selects only the newest turn. If the
newest turn is not `inProgress`, steer and interrupt refuse. This rule handles a
measured runtime condition in which crash-orphaned older turns remain
`inProgress` indefinitely.

**Live-verified 2026-09-01:** `thread/read {includeTurns:true}` returned
`list_turns is not supported yet` even though `includeTurns` appears in
`v2/ThreadReadParams.json`. Use `thread/turns/list`; never infer turn history
from `thread/read` on this runtime line.

Generated `v2/TurnSteerParams.json` defines an `AdditionalContextEntry`, but its
request `properties` do not expose an `additionalContext` member. Sending that
orphaned definition is **unverified and unsupported**. Treat tool-observed text
as untrusted at the host policy boundary instead.

## Status and listening

**Schema-derived:** `v2/ThreadStatusChangedNotification.json` defines status
types `active`, `idle`, `systemError`, and `notLoaded`, plus the active flags
`waitingOnApproval` and `waitingOnUserInput`.

**Implementation contract:** the listener opens with paged `thread/list`
requests using an explicit all-source `sourceKinds` set and
`useStateDbOnly:true`, both defined by `v2/ThreadListParams.json`. In `--all`
mode it watches only owned threads active in that opening snapshot. It requires
the exact owned row's schema-required `cwd` to match the durable lane seat before
accepting its status. For each active owned lane it establishes a metadata-only
`thread/resume {cwd:<seat>,excludeTurns:true}` subscription, requires both
returned cwd fields to match, and retains seat-verified `thread/read` polling as
a fallback.

Do not rely on cross-client notification broadcast. The supported behavior is
subscription-scoped and every event handler filters exact watched IDs.

`notLoaded` is normal persisted state. It is actionable only when a lane that
was expected to be working transitions there. A non-empty active flag wakes the
operator as `WAITING`; `idle`, `systemError`, and unexpected `notLoaded` wake it
as stopped/error boundaries.

**Live-verified 2026-09-01:** a read-only census returned a large majority of
persisted rows as `notLoaded`, confirming that it is not itself proof of a dead
runtime. Process listings, silence, and client exit are likewise not lane
liveness receipts.

## Listing, reads, and diagnostics

**Schema-derived:** `v2/ThreadListParams.json` and
`v2/ThreadListResponse.json` define cursor pagination. Follow `nextCursor` until
null before claiming a complete census.

**Implementation contract:** `scripts/rpc.js` is default-deny and permits only:

- `account/rateLimits/read`
- `model/list`
- `thread/items/list`
- `thread/list`
- `thread/loaded/list`
- `thread/read`
- `thread/turns/list`

Content-bearing thread reads require `--repo-root`, an exact registry-owned
Codex thread ID, and a matching recorded runtime identity. Notifications are
redacted. Thread census results retain only status, timestamps, and source;
thread IDs, parent IDs, previews, names, local paths, and Git metadata are
removed from unrelated rows. There is no mutation override.

Pagination cursors are opaque transport values and are never printed by the
routine census projection. Direct `model/list` and `account/rateLimits/read`
calls intentionally return provider metadata; treat that output as sensitive
and do not place it in public logs.

## Retirement

**Schema-derived:** `v2/ThreadArchiveParams.json` identifies the thread to
archive and `v2/ThreadArchiveResponse.json` defines the acknowledgment.

**Implementation contract:** retirement requires a durable harvest SHA-256
before any provider mutation. The adapter proves the newest turn is inactive,
sends archive once, scans the complete bounded archived listing, and requires
exactly one matching thread whose schema-required `cwd` equals the durable lane
seat. Missing, malformed, mismatched, or duplicate exact rows fail closed before
provider retirement is marked verified. A managed worktree is removed
only when it was clean at harvest, its current HEAD matches the harvest receipt,
and its current tracked, untracked, and ignored-file census is clean. An external
seat is never removed. Once a
harvest or cleanup check observes dirt or changed HEAD, automatic cleanup is
permanently blocked pending manual review; later cleanliness does not make the
seat eligible again.

This census protects every file observed before removal. Git worktree removal
is not atomic with the census: another process running as the same user can
write a new ignored file after the final check and before Git removes the seat.
Stop the owned lane/provider execution before cleanup, and do not let unrelated
local writers target a managed seat during retirement. That same-user
concurrency window is outside the 0.2.x isolation boundary.

If cleanup fails after archive verification, the lane remains provider-retired
with a pending cleanup journal. A transient local Git/filesystem failure is
`CLEANUP_RETRYABLE`; a later retry performs no provider mutation. An observed
dirt, changed HEAD, seat/repository mismatch, or other unsafe invariant is
`CLEANUP_BLOCKED` and remains preserved for manual review.
Preserving the seat leaves the refusal intact. After the owner manually removes
the exact managed seat, only an exact-lane retirement with
`--accept-manual-seat-removal` can journal that acknowledgement; it rejects a
surviving path entry or Git worktree row and requires the preserved branch at
the harvested HEAD. Fleet-wide reconciliation cannot infer acknowledgement
from disappearance. If the process stops after an ordinary eligible Git
removal but before the operation journal closes, the next retry verifies the
absence and completes the journal without this manual-removal gate.

## Durable state and failure classes

**Implementation contract:** the ownership registry lives under
`TRANSMOGRIFY_STATE_DIR` or the platform state directory, outside the repository and
Git common directory. It records an installation UUID, canonical repository
identity, lane IDs, exact provider identities, seat identities, capability
semantics, and one pending operation pointer per lane. Operation details are
monotonic: phase transitions atomically replace the record, existing detail keys
are immutable, and later phases may add new receipt keys. The record is durable,
but it is not an append-only transition log.

State directories are current-user-owned mode `0700`, and JSON records are mode
`0600`. Managed `WORKTREES` roots are current-user-owned mode `0700`; configured
roots refuse a group/world-writable nearest existing ancestor.

Mutations use three outcomes:

| Outcome | Meaning | Required next action |
| --- | --- | --- |
| Confirmed | Exact provider receipt observed | Continue lifecycle |
| Not delivered | Provider mutation proven absent | A new authorized operation may be attempted |
| Unknown | Provider may have received it | Observe and reconcile; never replay blindly |

Public error projection defaults to `Unknown`. Only an explicit, tested
non-delivery or pre-dispatch refusal may report `Not delivered` or
`notAttempted`. A multi-stage failure may report a verified earlier phase—for
example, Claude stop verified with archive not attempted—without claiming the
whole retirement succeeded.

The CLI exits 0 for confirmed results, 2 for safe refusals and precondition
failures, and 3 for transport/protocol/provider uncertainty. Server JSON-RPC
errors preserve numeric `code` and string `message` internally as defined by
`JSONRPCErrorError.json`; routine public CLI output uses fixed redacted
messages.

Claude runtime and worker epochs are append-only identity receipts inside the
current lane record. Reconciliation may add a verified CLI transition only when
the account, config, provider IDs, seat, worker binary, process birth, and socket
identity remain exact; it never overwrites the spawn runtime. See
[Claude Code integration](CLAUDE-CODE.md#measured-compatibility-tuple).

Parent/child delivery is also durable state, not a transient process callback.
An exact parent context owns immutable dispatch reservations and sequenced child
events. The parent must acknowledge an event by its exact ID and digest; a
missing or malformed acknowledgement cannot suppress redelivery. Every
unacknowledged event is returned again after a parent restart regardless of a
newer observation cursor. Observation may reconcile an exact incomplete spawn
journal, but it never infers provider creation from a title or elapsed time and
never replays an unknown mutation. The complete parent loop and event meanings
are in [Dispatch and lineage](DISPATCH.md).

## Security-relevant schema surface

**Schema-derived:** `ClientRequest.json` exposes authority-bearing methods beyond
the adapter. `v2/ThreadShellCommandParams.json` describes unsandboxed full-access
command execution. `v2/FsRemoveParams.json` accepts an absolute path and
recursive removal. `v2/ThreadDeleteParams.json` deletes by thread ID.

Therefore Transmogrify's accepted root-path loopback configuration is an
unauthenticated local control plane, not a safe general-purpose localhost API.
Codex documents authenticated remote WebSockets, but this release rejects
non-loopback endpoints and URL credentials. Bind the selected local runtime to
`127.0.0.1`, inspect listeners and clients, and never expose a generic mutation
proxy.

## Claude Code protocol boundary

Claude Code exposes a documented multi-session Remote Control server, but no
documented external local RPC equivalent to the Codex app-server lifecycle was
found in the surfaces verified for this release. Its public CLI follow-up,
measured local execution identity, Remote Control visibility, and pinned private
archival behavior are documented separately in
[CLAUDE-CODE.md](CLAUDE-CODE.md). Those claims are not derived from the Codex
schema.
